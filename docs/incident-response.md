# 対応管理表(壊れた・盗まれた・漏れたとき)

何かが壊れた、盗まれた、漏れたときに「いま何がどうなっていて、次に何をするか」を
1か所で追うための表。2026-09-14 作成。

**起きたら、直す前にまず1行足す。** 直してから書こうとすると、途中で別の問い合わせが
来たときに「あれはどこまでやったか」が分からなくなる。1行あれば、翌日の自分にも
Claude Code にも「続きはここから」と言える。

状況を追う表(§1)と、その時系列の記録(§3)は、この文書を直接編集して更新する。
何が起きうるかと最初にやることは §4 に資格サイト固有の内容で書いてある。
初めて開いたときは §1 の記入例と §4 の該当項目だけ読めばよい。

## 2. 記入のルール

### ID

`INC-YYYYMMDD-NN`。発生日(気づいた日でよい)と、その日の連番。
例: `INC-20260914-01`。

### 区分

| 区分 | 使うとき |
|---|---|
| 障害 | サイト・決済・メールなど、動くはずのものが動かない |
| 盗難・紛失 | PC・スマホ・アカウントなど、持ち物や権限を失った |
| 漏えい | 鍵・パスワード・個人情報・有料コンテンツが外に出た(疑いを含む) |
| 不正利用 | 盗難カードでの購入、受験権の流用、コピーサイトなど、他人による悪用 |
| 内容の誤り | 解説・問題・試験情報の間違い。障害ではないが、同じ表で追うと漏れない |

### 深刻度と着手の目安

| 深刻度 | 定義 | 着手 |
|---|---|---|
| S1 | 売上か個人情報に直結。決済できない、払ったのに受験できない、鍵や個人情報が漏れた、サイト全体が落ちた | 気づいた当日 |
| S2 | 一部の機能が壊れている。メールが飛ばない、特定資格の模試だけ開けない、広告リンク切れ | 3日以内 |
| S3 | 見た目・文言・解説の誤り。利用者が困るが、売上と信用をすぐには損なわない | 次のデプロイに載せる |

迷ったら1つ上にする。下げるのは後からでもできる。

### 状態

| 状態 | 意味 |
|---|---|
| 未対応 | 気づいたが、まだ手を付けていない |
| 対応中 | 手を付けている。「次にやること」に具体的な作業が入っていること |
| 確認待ち | こちらの作業は済み、外部の返事待ち(Stripe サポート、購入者の返信、ホスティングの削除対応など)。誰の何を待っているかを「次にやること」に書く |
| 復旧済み | 利用者への影響は止まった。再発防止か記録が残っている |
| 完了 | 復旧し、再発防止の判断(やる・やらない)まで書いた。「終了したもの」へ移す |
| 対応しない | 見送り。理由を §3 に書く。理由が無い「対応しない」は無し |

### 「次にやること」は動詞で書く

「様子見」「確認」ではなく「Stripe の webhook 配信履歴で 9/14 以降の失敗を数える」のように、
次に机に座ったとき何をするかが分かる粒度で書く。期限は、S1 は当日、S2 は3日後を既定にする。

### 見直し

月に1回この表を開き、「対応中」「確認待ち」のまま更新日が2週間以上前のものが
ないかを見る。あれば、進めるか「対応しない」に倒すかを決める。放置が一番まずい。

## 3. 対応の記録(時系列)

1件ごとに見出しを作り、やったこと・分かったこと・決めたことを時刻付きで書く。
表の「次にやること」を更新するたびに、ここにも1行足す。

### INC-20260901-01(記入例)決済メールが届かない

- 09-01 10:30 購入者から「メールが来ない」と問い合わせ。Stripe で決済は `paid` を確認
- 09-01 10:40 Stripe → 開発者 → Webhook で該当エンドポイントを見ると全件 `308 ERR`。
  レスポンスに `{"redirect":"/api/stripe-webhook/","status":"308"}`
- 09-01 10:45 原因: エンドポイント URL に末尾スラッシュが無い(`trailingSlash: true` で 308 が返り、
  Stripe はリダイレクトを追わない)。Stripe 側の URL を `…/api/stripe-webhook/` に修正
- 09-01 10:50 失敗していたイベントを Stripe の画面から再送。Resend のログで全件送信を確認
- 09-01 11:00 問い合わせ者に届いた旨の返信あり。再発防止として `docs/moshi2-setup.md` に記載 → 完了

## 4. 何が起きうるか と 最初にやること(早見表)

このサイトの構成(ログイン無し・DB 無し・Stripe が唯一の真実・Vercel で SSG)を前提にした
一覧。詳しい仕組みは `docs/moshi2-setup.md`。各項目は「気づき方 → 最初の5分 → 復旧の条件」の順。

### 4.1 壊れた

#### サイト全体が開かない

- 気づき方: 自分で開いて落ちている、GA4 のリアルタイムが 0、問い合わせ
- 最初の5分:
  1. Vercel のステータス(https://www.vercel-status.com/)。Vercel 側の障害なら待つしかない。表には「確認待ち」で載せる
  2. Vercel → プロジェクト → Deployments。直近のデプロイが失敗していないか、
     失敗なら **前の成功デプロイを Production に戻す**(Instant Rollback / Promote to Production)。
     戻してから原因を追う
  3. ドメインが切れていないか。`dig shikakumon.com` が引けない、レジストラから期限切れの
     メールが来ていないか(レジストラ: **要記入**)
- 復旧の条件: トップと資格トップと `/pii/moshi2/` が開き、購入ボタンが「準備中」を返さない

#### デプロイ(ビルド)が失敗する

- 気づき方: Vercel からの失敗メール、push したのに本番が変わらない
- 最初の5分: Vercel のビルドログを読む。`prebuild` の監査(`audit-questions` / `audit-moshi2` /
  `audit-practice-routes`)が落としているなら、それは**データの不備を本番に出さずに止めている**
  状態。前の成功デプロイが出続けるので S3 でよい。監査の出力どおりにデータを直す
- 復旧の条件: `npm run build` がローカルで通り、Vercel の本番デプロイが成功

#### 購入ボタンを押すと「決済は現在準備中です。」

- 原因の当たり: 本番の `STRIPE_SECRET_KEY` が無い・失効・ロール済み。
  環境変数を入れた/変えたあとに **Redeploy していない**(Vercel の環境変数はデプロイ時の値が固定される)
- 最初の5分: Vercel → Settings → Environment Variables で Production に鍵があるか →
  無ければ入れて Redeploy。あるなら Stripe → 開発者 → API キーで失効していないか
- 手元での診断: `npm run stripe:check`
- 復旧の条件: 本番で購入ボタンが Stripe の決済ページへ進む(テストカードは本番では使えないので、
  決済ページが開くところまで)

#### 資格の第2回模試ページ自体が「準備中」表示

- 上とは別物。`loadMoshi2()` が `null` を返している = 問題数が `moshi2-products.ts` の仕様と
  合わない。データファイル(`src/lib/<cert>-moshi2.ts`)を壊した可能性が高い
- `node scripts/audit-moshi2.mjs` を手元で回し、指摘を直してデプロイ

#### 払ったのに受験できない(S1。問い合わせで気づくことがほとんど)

- 最初の5分: 購入者に「決済に使ったメールアドレス」を聞く。Stripe → 支払い でそのアドレスを検索し、
  `paid` であること、metadata の `certId` と `kind: moshi2` を確認する。ここで決済が無ければ
  決済自体が失敗している(カード側で弾かれた)ので、その旨を返す
- 次に見る順:
  1. Stripe → 開発者 → Webhook → このサイトのエンドポイント → 配信履歴。該当イベントが
     `200` 以外(`308`=URL の末尾スラッシュ抜け、`400 invalid_signature`=`STRIPE_WEBHOOK_SECRET`
     の取り違え。Studio 用の `whsec_` を入れると必ずこれ)なら原因を直し、**その画面から再送**する。
     再送すると新しい受験用リンクがメールで届く。何度再送しても端末数の上限は減らない
  2. 配信は `200` なのに届いていない → Resend → Emails で送信ログ。バウンス・迷惑メール判定なら
     購入者に迷惑メールフォルダを見てもらい、それでも無ければ再送
  3. `RESEND_API_KEY` が Production に無い → メールは送られない(webhook は `mailed: false` で 200 を返す)。
     入れて Redeploy し、再送
  4. Vercel → Logs で `stripe-webhook:` `sendMail:` `redemptions:` で始まる `console.error` を探す
- どうしても復旧できない、または試験日が過ぎてしまった: `/tokushoho/` の記載どおり
  **サイト側の不具合なら全額返金**(Stripe の支払い画面から返金)。返金したことを表に書く
- 復旧の条件: 購入者から「開けた」の返信、または返金完了

#### 「このリンクは使えません」と言われる(メールの受験用リンク)

- 原因の当たり: リンクが途中で切れている(メールソフトの折り返し)、発行から400日超、
  `ACCESS_SECRET` を変えた(→ §4.2 参照。全購入者に影響する事故)
- 対処: Stripe で決済を確認 → webhook のイベントを再送して新しいリンクを送る

#### 「端末の切り替えが30日間で5回の上限に達しました」

- 仕組み: 台帳は Stripe の PaymentIntent の metadata `redeemed`(回数)と `redeemedFrom`(起点)。
- 正規の購入者だと判断したら: Stripe → 支払い → 該当決済 → メタデータ を編集し、
  `redeemed` を `0` にする(または削除)。その場で復旧する。再デプロイは要らない
- 明らかな流用(短時間に多端末)なら手を出さず、期日まで待ってもらう。文面に復旧日が出ている

#### 請求額がおかしい(桁が違う・別の商品名)

- JPY はゼロ十進通貨で `priceJpy` がそのまま円になる。`npm run stripe:check` で確認
- 取り過ぎていたら Stripe から差額を返金し、購入者に一報。値段は `src/lib/moshi2-products.ts` の1か所

#### 購入メールの差出人が迷惑メール扱いされる

- Resend → Domains で `shikakumon.com` の DKIM/SPF が緑か(認証は Studio 側で済ませてある。
  DNS を触ったあとに壊れることがある)

#### 広告(A8)のリンクが切れている・別のページに飛ぶ

- 気づき方: A8 の管理画面で「提携解除」「プログラム終了」、クリックはあるのに成果 0
- 対処: 差し替え先は `src/lib/affiliate-links.ts` と該当の `*CourseAd.tsx` の**両方**
  (片方だけ直すと取りこぼしが続く)。代替の広告主は `docs/affiliate-growth-audit.md` §4
- 収益機会の損失なので S2。ページは壊れていない

#### 問い合わせ・合格報告が届かない

- 合格報告は `/api/pass-report` が Resend で運営宛メールを送るだけで、**どこにも保存されない**。
  `RESEND_API_KEY` が無いと投稿は静かに消える。Resend のログで送信を確認する
- 問い合わせ先の Gmail 自体が読めない場合は §4.2 の「Google アカウント」へ

#### 解説・問題・試験情報の誤り(S3)

- 直す場所: `src/content/<資格>/` の該当 `.md`(資格によっては `src/lib/<資格>-questions.ts`)。
  直したら `npm run build` を手元で通す(`prebuild` の監査が正解位置の偏りなどを機械で検査する)
- 受験料・合格基準など**事実の誤り**は S2 に上げる(信用に直結し、合格報告の掲載基準でも
  「事実と異なる試験情報」を掲載不可にしている以上、自分のサイトが間違っていてはいけない)

### 4.2 盗まれた・漏れた

共通の原則: **鍵が「見られたかもしれない」時点で漏れたとみなす。** 確証を待つ間に使われる。
ただし `ACCESS_SECRET` だけは変えると購入者全員が締め出されるので、影響を読んでから変える(下記)。

#### 作業用 PC の紛失・盗難

- PC には `.env.local`(`STRIPE_SECRET_KEY` のテスト鍵、場合によっては本番の `ACCESS_SECRET`)、
  ブラウザにログイン済みの Vercel / Stripe / GitHub / Google / Resend / A8 のセッションがある
- 別の端末から、この順に:
  1. Google: パスワード変更 → 「すべての端末からログアウト」→ 転送設定とフィルタに覚えのないものが無いか
  2. GitHub: Settings → Sessions で全ログアウト、Personal access tokens と SSH keys を全部失効
  3. Vercel: Settings → セッションの失効、トークンの削除
  4. Stripe: セッションの失効、`STRIPE_SECRET_KEY` を**ロール**(§6。Studio の Vercel も更新)
  5. Resend: API キーを削除して作り直す(§6)
  6. A8 / もしも: パスワード変更、**報酬の振込先口座**が変わっていないか
  7. OS の「デバイスを探す」でリモートロック/消去
  8. `.env.local` に本番の `ACCESS_SECRET` が入っていたなら §6 の手順で入れ替える。入っていなければ変えない
- 復旧の条件: 上の全アカウントで2段階認証が有効、鍵の入れ替えが済み、Stripe に覚えのない
  返金・出金先変更が無いことを確認

#### スマホの紛失(2段階認証の端末)

- 各サービスのバックアップコードを別に保管していれば、それでログインして認証端末を差し替える。
  無ければ復旧手続き(Google は数日かかることがある)。**今、バックアップコードがどこにあるかを
  §5 の表に書いておく**

#### Google アカウント(問い合わせ先 Gmail)の乗っ取り

- 最も影響が大きい。他サービスの復旧先メールで、購入者・投稿者のメール(個人情報)がたまっており、
  Stripe の通知も届く
- 最初の5分: Google のアカウント復旧 → パスワードとバックアップ手段を変更 → 全端末からログアウト
  → **転送設定・フィルタ・アプリのアクセス権**を確認(乗っ取りは転送ルールを残していく)
- その後: 他の全サービスのパスワードを変える(このメールでリセットできるため)。
  受信箱の個人情報が読まれた可能性があるなら §4.2 末尾の「個人情報の漏えい」へ

#### GitHub の乗っ取り、または覚えのない push

- Vercel は push で自動デプロイする。しかも `prebuild` はリポジトリ内のスクリプトを **Vercel の
  ビルド環境(環境変数が見える)** で実行する。つまり GitHub を取られた時点で
  **Vercel の環境変数はすべて漏れたとみなす**
- 最初の5分: 直近のコミットとデプロイを確認 → 不審なら前の成功デプロイに戻す →
  GitHub のパスワード・トークン・SSH 鍵・デプロイキーを全部失効 → §6 の鍵をすべて入れ替える
- コミットの取り消しは `git revert`(履歴を消さない)

#### Vercel の乗っ取り

- 環境変数が読めるので §6 の鍵はすべて漏れたとみなす。加えて **ドメインの向き先**と
  **デプロイの内容**を確認する(別のサイトを shikakumon.com で配信されうる)
- Vercel のパスワード・トークン・チームメンバーの確認 → 鍵の総入れ替え

#### Stripe の乗っ取り

- 被害: **出金先口座の変更**(売上の窃取)、返金の乱発、顧客メールアドレスの閲覧
- 最初の5分: Stripe にログインし直してパスワード・2段階認証を変更 → Settings の出金先と
  チームメンバーを確認 → API キーをロール → 覚えのない返金・出金が無いか
- Stripe と Studio はアカウント共通なので Studio 側の売上も見る。Stripe サポートに連絡
- 顧客のメールアドレスが見られた可能性 → 「個人情報の漏えい」へ

#### A8 / もしも の乗っ取り

- 被害: 報酬の振込先の書き換え、リンクの差し替え。振込先とプロフィールを確認し、
  パスワード変更。サイトの収益が落ちるだけなので S2

#### `ACCESS_SECRET` の漏えい

- できてしまうこと: 受験権 cookie とメールのリンクを偽造できる = 全資格の有料模試を無料で開ける
- 変えると: **既存の購入者全員が締め出され、送付済みの受験用リンクも全部無効**になる
- 判断: 基本は変える(偽造が可能な状態を放置しない)。ただし手順を先に読む:
  1. 新しい値を作る `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`
  2. Vercel の Production を更新 → Redeploy
  3. **過去30日以内の購入**: Stripe → 開発者 → Webhook → 該当イベント(`checkout.session.completed`)を
     1件ずつ再送する。webhook は今の鍵で署名し直したリンクをメールするので、購入者は
     新しいメールのリンクを開くだけで復旧する。端末数の上限は消費しない
  4. **30日より前の購入**: Stripe はイベントを再送できない。再発行スクリプトは**未整備**。
     問い合わせが来たら Stripe で決済を確認し、返金するか、`src/app/api/stripe-webhook/route.ts`
     の署名とメール送信部分を切り出したスクリプトを作って手動で送る(作ったら `scripts/` に置き、
     この行を書き換える)
  5. 購入者向けの告知文を用意しておく(§7)
- 漏れた経路を必ず突き止めて §3 に書く(git の履歴、ログ、PC)。経路が分からないまま
  鍵だけ変えても、また漏れる

#### `STRIPE_SECRET_KEY` の漏えい

- できてしまうこと: 決済の照会、返金、顧客情報の閲覧、Checkout の作成(このサイトと Studio の両方)
- Stripe → 開発者 → API キー → **ロール**(すぐ失効させる)。新しい鍵を **このサイトと Studio の両方の
  Vercel** に入れて両方 Redeploy。入れ替えるまで両サイトの購入ボタンが「準備中」になる
- Stripe のログ(開発者 → ログ)で覚えのない API 呼び出しが無いか

#### `STRIPE_WEBHOOK_SECRET` の漏えい

- できてしまうこと: 偽の「決済成立」イベントを送り、好きなメールアドレスに受験用リンクを送らせる
  (= 有料模試を無料で入手)
- Stripe → Webhook → このサイトのエンドポイント → シークレットをロール → Vercel → Redeploy。
  このサイト専用の値なので Studio は関係ない。入れ替えるまでは署名不一致で 400 になり
  メールが止まるが、Stripe が自動再送するので決済は失われない。入れ替え後に失敗分を再送

#### `RESEND_API_KEY` の漏えい

- できてしまうこと: `noreply@shikakumon.com` を騙ったメール(フィッシング)を送れる。
  信用に直結するので S1
- Resend → API Keys で削除 → 新しいキー → Vercel → Redeploy。Studio と同じキーを使っているなら
  Studio 側も更新。Resend の送信ログで覚えのない送信が無いか

#### 有料模試の紙面(印刷ページの PDF)が出回った

- 仕組み上、PDF は受験権無しに開ける(`docs/moshi2-setup.md` §3 の「限界」)。透かしは未実装
- 対処: 回収はできない。掲載先が分かれば、ホスティング事業者かプラットフォームに著作権侵害として
  削除を求める(送信防止措置依頼 / DMCA)。表には「確認待ち」で載せ、依頼先と日付を書く
- 売上が実際に落ちているかを Stripe で見てから、透かしの実装(購入者のメールアドレスを紙面に刷る)を
  検討する。落ちていないなら「対応しない」でよい

#### 受験用リンク・URL の流用

- 30日5回の上限で自動的に止まる。個別のリンクだけを無効にする手段は**無い**
  (無効にするには `ACCESS_SECRET` を変えるしかなく、全員に影響する)
- 疑いがあるときは Stripe の該当 PaymentIntent の `redeemed` を見る。上限に張り付いていれば
  流用の可能性。それ以上のことはしない

#### 無料の問題・記事のコピーサイト

- 気づき方: 特徴的な文を検索して見つかる、Search Console で同一タイトルの別ドメインが出る
- 対処: Google に著作権侵害の削除申請(検索結果からの除外)、ホスティングへの削除依頼。
  検索順位を取られるのが実害なので S2。「確認待ち」で追い、2〜4週間で結果を見る

#### 盗難カードでの購入・チャージバック

- 気づき方: Stripe から不審請求(Dispute)の通知、Radar の警告
- 対処: 明らかに不正なら**争わず先に返金**する(争って負けると手数料が余分にかかる)。
  正規の購入で「身に覚えがない」と言われたケースは、カード明細に出る名前が原因のことがある
  (`docs/moshi2-setup.md` §3「カード明細に出る名前」)。Stripe の期限内に証拠を出す
- 頻発するなら Radar のルールを検討

#### 個人情報の漏えい(疑いを含む)

- このサイトが持っている個人情報の置き場所:
  - Stripe: 購入者のメールアドレス・決済情報(カード番号は Stripe が保持し、こちらでは見えない)
  - Gmail: 問い合わせ、合格報告(本文に受験時期・学習期間などが入る)
  - Resend: 送信ログ(宛先メールアドレス)
  - Vercel のログ: 原則メールアドレスは出さない設計だが、エラー出力に混ざる可能性はある
- 最初の5分: 漏れた範囲(誰の・何が・何件)を、分かる限りで §3 に書く。分からないことも書く
- 報告義務の確認: 個人情報保護法の漏えい等報告は、不正アクセス等の故意による漏えい、
  財産的被害のおそれ、要配慮個人情報、1,000人超のいずれかで対象になる。**速報は概ね3〜5日以内、
  確報は30日以内(不正目的の場合は60日以内)** に個人情報保護委員会へ、あわせて本人への通知。
  規模が小さくても事業者としての義務はある。要否と期限は個人情報保護委員会のサイトで
  その時点の要件を確認して決め、決めた根拠を §3 に書く
- 本人通知の文面は §7

## 6. 秘密情報の一覧と、変えたときの影響

| 名前 | 置き場所 | 漏れるとできてしまうこと | 変えると | 変え方 |
|---|---|---|---|---|
| `ACCESS_SECRET` | Vercel(Production) | 受験権の偽造(全資格の有料模試が無料で開く) | **購入者全員が締め出される**。送付済みリンクも無効 | §4.2 の手順。生成 → Vercel → Redeploy → 30日以内の購入は webhook 再送 |
| `STRIPE_SECRET_KEY` | Vercel(このサイトと Studio の両方) | 決済の照会・返金・顧客情報の閲覧 | 更新まで両サイトの購入ボタンが「準備中」 | Stripe でロール → 両方の Vercel → 両方 Redeploy |
| `STRIPE_WEBHOOK_SECRET` | Vercel(このサイトのみ) | 偽の決済イベントで受験用リンクを送らせる | 更新までメールが 400 で止まる(Stripe が再送するので決済は失われない) | Stripe のエンドポイントでロール → Vercel → Redeploy → 失敗分を再送 |
| `RESEND_API_KEY` | Vercel(Studio と共用の可能性あり) | ドメインを騙ったメール送信 | 更新まで購入メール・合格報告メールが止まる | Resend で削除と再発行 → Vercel → Redeploy |
| `MAIL_FROM` | Vercel(任意) | — | 差出人が変わるだけ | — |
| `NEXT_PUBLIC_GA_ID` | Vercel(公開情報) | 偽データの送信程度 | 計測が途切れる | — |
