# X などでつぶやきたくなる企画の設計（2026-10-25、点検を受けて修正）

## もし1つだけやるなら

1. 賃管士（11/15）と管業（12/6）の試験の前の7日間だけ、その回を受ける人全員に同じ10問を出す。記録は1つのブラウザにつき1回目だけ残す。結果は答えを明かさない○×の並びにして、X と LINE に送れるようにする。名前は「試験前の10問」。
2. 送られたリンクを開いた人は、登録しなくても同じ10問をすぐ解ける。解き終えたら、投稿した人の点と並べて見られる。サーバーには何も保存せず、順位も見返りも付けない。
3. 作り始める前に、半日〜1日の段階0を済ませる。中身は次の2つ。
   - いまの模試の投稿を直す。宣伝の言い回しを外し、utm を付け、リンク先のずれを直す。
   - GA4 で4つを確かめる。share_click の実数、拡張計測の離脱クリックの設定、資格ごとの利用、模試の完了数。結果は、対象を選び直すときと、続けるかを決めるときの物差しにする。

## 調べ方

- 調査は4つ。
  1. 学習・クイズ・検定で投稿が広がった事例。
  2. X で資格の勉強をしている人が、実際に何を投稿しているか。
  3. 投稿から次の投稿までの輪が切れる場所と、不正・プライバシー・法の扱い。
  4. このサイトで作れるか。コードを読み、使い捨ての Next アプリで next/og と ISR の動きを確かめた。
- 企画案は10。切り口は5つで、それぞれに2案ずつ出した。
  - 週替わりの共通問題
  - 挑戦状リンク
  - 要望どおりの順位
  - 学習記録カード
  - 試験日に合わせたイベント
- 評価のしかた
  - 案ごとに3人が5点満点で採点した。見たのは次の3つ。
    - 広がり: 輪がつながるか。
    - 価値: 学習の役に立つか、サイトのトーンに合うか、投稿する本人が気まずくないか。
    - 作れるか: コード・プライバシー・不正・法の面から見た。
  - これとは別に反証役が1人つき、いちばん強い反論と、それでも効く条件を出した。
  - 下の企画案は、評価者が出した直し（improvements）を取り込んだ形で書いている。
- 点検で10件の指摘を受け、この版で直した。
- 調べられなかったこと
  - X の投稿ページは開けなかった。Web の根拠はすべて検索結果の要約で、ページ本文は読んでいない。
  - Web 検索の上限（200回）に評価の段階で達し、点検と修正の段階でも達したままだった。そのため、外部の主張は確かめ直せていない。この版で足した LINE の共有 URL の形も、Duolingo の数字がどの出典の主張なのかも、確かめていない。
  - GA4 の実数は見ていない（share_click、資格別の利用、mock_complete の件数）。
  - Studio のリポジトリは見られない。
  - 法的な整理は解説記事の要約に基づくもので、弁護士の判断ではない。
  - 次の点は実機で確かめていない。
    - X のアプリ内ブラウザで投稿画面が開くか。
    - t.co を通ったあとも、URL の「#」以降が残るか。
    - Web Share で渡した画像を X が受け取るか。
    - Safari と Chrome の投稿ボタンから、X アプリ・LINE アプリに渡るか。
    - X と LINE のアプリ内ブラウザで、記録が普段のブラウザと別に残るか。

反証は10案すべてで成立した。いちばん多い理由は規模である。

- 模試を解き終える人は90日で87人。全資格を合わせて週に約7人、資格ごとでは週0.25〜0.5人になる。
- 28日の検索クリックは約2,450（週に約610）。
- 評価者たちの試算（推測）では、1件の投稿が生む次の投稿は多くて0.1件前後。輪が自分で回り続けることはない。

どの案でも、期待できるのは次の2つにとどまる。

- 投稿1件が数人を連れてくる、小さな上乗せ。
- 今いる利用者の学習の役に立つこと。

そのため、各案に「効く条件」を付けた。

## 企画案（価値の高い順）

### 案1 試験前の10問（賃管士・管業から）

一言: 試験の7日前から試験日まで、その回を受ける人全員に同じ10問を出す。記録は1つのブラウザにつき1回目だけ残す。結果は答えを明かさない○×の並びで送れる。送られた人は、リンクから同じ10問に挑める。

効く条件（反証を受けて絞ったところ）
- 対象は、同じ日に受ける人が多い回に絞る。
  - 受験者数（令和7年度）は、賃管士 31,792人、宅建 245,463人、管業 14,435人。出どころは src/content/columns/chintai-takken-hikaku.md:19 と docs/affiliate-growth-audit.md §5.2 で、どちらも検索結果の一致で確かめた値。協会の公式発表では確かめていない（§5.2 自身が「運営が一次情報で確認すること」としている）。
  - 宅建（10/18）と賃管士（11/15）はひと月差で、同じ年に両方受けられる（同じコラムに記載）。宅建を終えた人が続けて賃管士を受ける流れがあるかは推測。
  - X に勉強垢の集まりがある回かどうかも推測で、件数は数えていない。
- 期間制の IBT/CBT（福祉住環境2級・eco は 11/12〜12/3）は外す。人によって受ける日が違うため。
- 目的は次の2つに置く。輪で増え続けることは期待しない。
  - 試験前の利用者が、最後に確かめる場にする。
  - 投稿1件ごとに、小さな上乗せを得る。
- 次の窓へは、併願の流れでつなぐ。賃管士（11/15）から管業（12/6）までは3週間ある。
- 対象の選び方は、段階0で GA4 の資格別の利用を見て確かめ直す（MVP の節）。
- 続けるかどうかは、2回の窓の数字を見て決める（MVP の節）。

利用者の体験
1. 見る: 窓の間だけ、次の場所に「11月15日（日）の試験の前に: 試験前の10問」を出す。
   - 資格トップの、試験日カウントダウンのすぐ下。
   - 直前対策コラム（chintai-chokuzen / kangyo-chokuzen）。
   - 問題ページの答え合わせの後。分野の途中の問題では「まとめて解くなら」の行に、リンクを1つ足す。分野の最終問では、行の代わりに「この分野の問題は以上です」のカードが出るので、その一覧の先頭に足す。新しい枠は作らない。
2. 解く: 全員が同じ順で10問を解く。解いている間は正誤を出さず、10問目のあとにまとめて採点する。記録は、このブラウザでの1回目だけを残す。
3. 投稿: 結果画面で「Xに投稿」「LINEで送る」「共有（スマホ）」「文面をコピー」を選べる。点を入れずに送る選択肢も、同じ大きさで出す。結果の先頭の部分は、スクショを貼る人のために、サイトの URL まで含めてスマホの1画面に収める。
4. 見た人が来る: 着地ページでは、投稿した人の点が1行だけ見え、そのすぐ下から問1を解ける。
5. その人も投稿する: 解き終えた画面に、同じ送り方のボタンが出る。
6. 窓が閉じたら: ページは答えと解説つきのアーカイブになり、何度でも解ける。
   - 投稿ボタンは出さず、間違えた問題の分野ページへ案内する。
   - 賃管士の結果画面からは、管業の試験前の10問（11/29 から）へ案内する。

投稿の文面と見た目の例（数字は例）
```
（1行目は空けておく。本人のひと言用。X で先頭の改行が残るかは実機で確かめる）
賃貸不動産経営管理士 試験前の10問（11/15 試験まであと6日）
10問中8問
○○×○○ ○○○×○
同じ10問を解けます（登録不要）
#賃貸不動産経営管理士
https://shikakumon.com/shikenmae/chintai/20261115/8/?utm_source=x&utm_medium=social&utm_campaign=shikenmae
```
- 全問正解のときだけ「10問中10問（全問正解）」と書く。
- 文面に入れないもの
  - 判定の言葉（「合格圏」「あと一歩」など）。
  - 「無料」「おすすめ」「予想」「的中」。
  - 絵文字。
  - 問題文・正解・分野名。
- 試験の当日は「（11/15 試験当日）」と書き、「あと0日」とは書かない。
- 「約◯分」は書かない。根拠が無いため（10問の文字数は、資格によって約1,300〜3,800字ある）。所要時間は、moshi_complete の minutes÷size の実測から出せるようになるまで載せない。
- ハッシュタグは、資格ごとの対応表で決める。
  - 公開前に運営が X で、どちらの表記の投稿が多いかを見て選ぶ（例: #賃管士 と #賃貸不動産経営管理士）。
  - 対応表に無い資格には付けない。
- OG 画像は回ごとに1枚にし、点は入れない（MVP の節）。

着地ページ
- URL は /shikenmae/<資格>/<試験日>/<点>/。点は 0〜10。noindex で、sitemap には載せない。
- 最初の画面には2行だけ出し、そのすぐ下に問1を置く。説明だけの画面は挟まない。
  - 「投稿した人の結果（自己採点）: 10問中8問」
  - 「11月15日（日）の試験の前の10問・登録不要」
- 「この点は、投稿した人のブラウザで採点したものです」は、問1の下か結果画面に小さく置く。投稿者を疑う文として目立たせない。

必要な仕組み: サーバーへの保存は無い。
- 10問のセットは、運営が確定した JSON をコミットする。
- ページはビルド時に作る（1回の試験につき12枚）。
- 詳しくは MVP の節に書く。

方針との関係
- 方針の内側に収まる。
  - 順位・バッジ・掲示板・見返りは作らない。
  - 学習履歴は端末の中に置いたまま。
  - 年齢・学年・学校など、年齢にかかわる情報は尋ねないし集めない。
- プライバシーポリシーには3か所足す。GA4 に送る値の一覧、URL に得点が入ることの説明、削除の対象。文案は MVP の節にある。
- 端末の記録から作った値（この端末にその回の結果があるか、など）は GA4 に送らない。調査の区分Bにあたるため。
- 投稿した人との1対1の比較を方針の内側と見るかは、ユーザーに決めてもらう。

不正・荒れ・法的な注意
- 得点は端末で採点していて、URL の点も書き換えられる。順位も景品も無いので、書き換える動機は小さい。
- 自由に入力できる欄を作らないので、サイトの中で見張るものは無い。
- 人数・平均・分布は出さない。人数が少なく、1人の点がそのまま分かってしまうため。
- ステマ告示の「事業者の表示」には当たりにくいと読める（推測）。見返りが無く、文面は事実だけで、本人が書き換えられるため。
- 「本番に出た」「的中」と受け取れる声は集めないし、載せない。優良誤認のおそれと、試験の守秘義務があるため。
  - 既存の合格報告のお願いは「当サイトの問題が本試験とどれくらい近かったか」を尋ねているので、この企画のアーカイブの近くには置かない。
  - 結果画面にもアーカイブにも、本試験の問題と比べるよう促す文言は置かない。

工数: M（5〜7日。推測）。ほかに、運営が10問のセットを確定する作業が1回につき1〜2時間かかる。

効果の測り方: MVP の節を参照。窓ごとに集計する。

### 案2 模試・本番形式テストの結果投稿（まず手直し、画像カードは後）

一言: いまの模試の投稿の文面とリンクを直し、本番形式テストにも投稿ボタンを付ける。得点・合格基準・分野のマス目を載せた画像カードは、投稿が実際に出てから作る。

効く条件
- 手直しの部分（段階0、工数 S）はすぐやる。基準の数字を取るためと、いまあるずれを直すため。
- 画像カード（段階1）は、段階0から4〜8週のうちに投稿経由の来訪が出たときだけ作る。
- 段階1の対象は、合格基準を「問数1本」で描ける模試に限る。次の模試では、基準線1本の絵が結果画面の判定と食い違ってしまうため外す。
  - 点数で合否が決まる模試: aia・bijimane・dxa・eco・fukushi2・xray
  - 課題ごとに足切りがある模試: dxp・hoikushi・isf・itpass・pii・touhan・xray

利用者の体験: 模試を採点すると、結果画面に「この結果を投稿する」ボタンが出る。本番形式テスト（27ページで共通の MockExam）にも同じボタンを置く。

投稿の文面と見た目の例（段階0。数字は例）
```
賃貸不動産経営管理士 模擬試験 第1回（シカクモン）
50問中41問正解（82%）
#賃貸不動産経営管理士
https://shikakumon.com/chintai/moshi/?utm_source=x&utm_medium=social&utm_campaign=moshi_share&utm_content=chintai
```
- いまの文面（「…・合格圏でした。シカクモンで無料受験中」）から、宣伝の言い回しと判定の言葉を外す。資格名を先に書き、サイト名は括弧に下げる。
- 本番形式テストは、ページの名前（例 src/app/kashikin/mock/page.tsx:8,30 の「本番形式テスト」）に合わせて書く。例は「管理業務主任者 本番形式テスト（シカクモン）／20問中14問正解（70%）」（数字は例）。「ランダム20問テスト」という別の名前は使わない。
- 段階1の画像カードでは、基準線に「合格ラインの目安 38問（令和7年度の基準）」と書く。分野のマス目を載せるかは、投稿する本人が選べるようにする。

着地ページ
- 段階0では、いまの模試トップ（本番形式テストなら、そのページ）のまま。
- 段階1では /kekka/<資格>/<種類>/<値>/ を作る。上から次の順に並べる。
  1. 「まず1問」
  2. 「本番形式テスト（20問・時間制限なし）」
  3. 「同じ第1回を受ける」（所要時間つき。同じブラウザなら途中から再開できる）
- 訪問の52%がスマホなので、120分の模試を一番上にしない。

必要な仕組み: サーバーへの保存は無い。

段階0でやること
- 文面を上の形に直し、utm を付ける。
- 結果の先頭の部分の下に、小さく「シカクモン shikakumon.com/chintai/moshi/」を入れる。結果画面のスクショが広がったときの入口にするため。いまの結果画面には URL もサイト名も無い。
- share_click に placement=moshi_result を足す。place=moshi は、過去のデータとの連続のために残す。本番形式テストの新しいボタンは placement=mock_result だけを送り、place は送らない。
- GA4 の拡張計測で「離脱クリック」が有効かを、管理画面で確かめる。
  - 有効なら、投稿リンクの href（投稿文）が、click イベントの link_url として GA4 に載っている可能性がある（推測）。
  - 模試の投稿文に入るのは得点と判定だけで、どちらもポリシーに書いてある範囲なので、模試のために急ぐことはない。
  - ただし MVP の投稿文には、問題ごとの○×が入る（調査の区分C）。そのため MVP の公開までに、次のどちらかにする。
    1. 離脱クリックを切る。A8 と Studio は affiliate_click・studio_click で測っているので、失うものは小さい見込み（推測）。
    2. 投稿ボタンを button にして、window.open で開く。スマホで X アプリや LINE アプリに渡らず、Web 版が新しいタブで開いてログインを求められるおそれがある（推測。実機では見ていない）。
  - 先に 1 を検討する。いまの a 要素は、どちらを選ぶか決まるまで替えない。
- ずれを2つ直す。
  - 生成AIアドバイザーの2級形式の結果が、1級形式の /gaia/moshi/ へリンクしている（src/app/gaia/moshi-2kyu/page.tsx は round=1・topPath=/gaia/）。2級形式と書き、/gaia/moshi-2kyu/ を指すように直す。
  - 有料の第2回の結果にも「無料受験中」と出る（Moshi2Gate.tsx）。文面から宣伝の言い回しを外せば解消する。リンク先は第1回（無料）のままでよい。

方針との関係: 方針の内側に収まる。得点を GA4 に送ることは、ポリシーにすでに書いてある。

不正・荒れ・法的な注意
- 投稿文に、第2回の購入の案内は入れない。利用者の投稿を広告にしないため（§5.3 と同じ考え方）。
- 段階1の画像には、自由に入る文字を入れない。値は検証してから描く。

工数
- 段階0: S（0.5〜1日）。
- 段階1: M〜L（6〜9日）。模試ごとの基準の台帳づくりと、日本語フォントの準備が要るため。

効果の測り方
- 作る前に、GA4 で次を確かめる。

### 案3 同じ10問を送るリンク（挑戦状）

一言: 本番形式テストに「10問」の選択を足し、解いた10問と自分の点をリンクにして送れるようにする。受け取った人は同じ10問を解き、2人の点を並べて見る。

効く条件
- 作るのは、案1・案2を出したあと、share_click が月に数十件ほど出てから。
- 主な送り先は、同じ時期に同じ試験を受ける身近な人（職場の同期、勉強仲間）とする。X で知らない人に広がることは期待しない。
  - ボタンは LINE・共有・コピーを先に、X を後に並べる。
- 画面では「挑戦状」「勝負」という言葉を使わず、「この10問を送る」と書く。

利用者の体験
- 本番形式テストで10問を選んで解く。既定の20問は残す。
- 結果画面で「この10問を送る」を押す。受け取った人がリンクを開くと、すぐ問1から解ける。
- 解き終えると「あなた 10問中9問／送った人 10問中8問」と並べ、問ごとの○×を比べる。勝ち負けの言葉は使わない。
- 「あなたの結果で送る」を押すと、同じ10問のまま送り返せる。
- 送った本人が、返ってきたリンクを開いたときは、解き直させずに比較を出す。そのために、送った10問と自分の○×を端末に残しておく。

投稿の文面と見た目の例（数字は例）
```
知的財産管理技能検定3級の10問で 10問中8問でした。
○○×○○ ○×○○○
同じ10問、解いてみませんか（登録なし）
https://shikakumon.com/onaji10/chizai/8/?q=0c0k1f2a0x1b0e2c0m1r&s=line
```
- 点を入れずに送る選択肢も用意する。点の低い人も送れるようにするため。
- 受け取った人が送り返す文面には、最初に送った人の点を入れない。LINE で個人的に送った点が、受け取った人の X 投稿で公開されてしまうため。
- LINE 向けの URL は短くする。utm は付けず、?s=line だけにする。

着地ページ
- /onaji10/<資格>/<点>/ はビルド時に作る（27資格×11通り＝297枚）。
- 問題の組（?q=）はブラウザ側で読み、サーバーでは読まない。サーバーで読むと、ページが毎回サーバーで描かれてしまう。
- 最初の画面は「知的財産管理技能検定3級の10問（送った人 8問）」の1行と、すぐ下の問1。
- noindex にする。

必要な仕組み: サーバーへの保存は無い。
- 問題番号は、slug の連番（変わらない値）を36進2文字にして作る。配列の何番目かは使わない。問題を足すと、古いリンクが別の問題を指してしまうため。
- 番号が欠けていたら「この10問の一部が見つかりませんでした」と出し、その資格の10問へ案内する。
- 10問のときは、結果画面から次の3つを外す。どれも10問では当てにならないため。
  - 合格ラインの判定
  - 分野別の棒
  - 「いちばんの弱点は…」
- 解説へのリンクは、EXAM_LIST の questionPathPrefix から作る（貸金だけ /q/）。

方針との関係
- 方針の内側に収まる。比べる相手は、本人が送った1人だけ。
- ポリシーには1文足す。「送ると、問題の番号と得点が URL に入り、開いた人と送り先のサービスに見えます」。
- 年齢にかかわる情報は集めない。

不正・荒れ・法的な注意
- URL の点は書き換えられる。ただ、だまされるのは送った人の知り合いだけで、動機は小さい。
- 自由に入る文字は無い。見返りも無い。
- 学校のグループなど、未成年どうしで送り合うこともある（推測）。名前・学校・学年を入れる欄は作らない。比較の画面には、勝ち負けの語も色分けも順位も出さない。

工数: M（5〜7日）。案1の部品を使い回せれば3〜4日。

効果の測り方
- share_click {channel: x|line|share|copy, placement: mock10_result|onaji10_result}
- onaji10_view {exam}、onaji10_start、onaji10_complete
  - 「この端末から送ったリンクか」は送らない。端末の記録から作る値で、区分Bにあたるため。
- 主に見るのは、utm と s= で分けた来訪数と、それが LINE と X のどちらに偏っているか。channel は、MVP の公開前にカスタム定義に登録しておく（MVP の節）。

### 案4 今週の10問（資格別）

一言: 資格ごとに「第N号」の10問を週替わりで出し、その週は全員が同じ順で解く。結果は○×の並びで送れる。号が URL に入るので、あとで見た人も同じ10問に挑める。

利用者の体験

投稿の文面と見た目の例（数字は例）
```

10問中8問
○○×○○ ○×○○○

https://shikakumon.com/weekly/itpass/3/
```

- 号のセットは、運営がスクリプトで作り、JSON をコミットする。

- 公開前の号を notFound にしない。

- 端末のキーは {資格: {号: …}} の形にする。学習履歴の削除の対象にも含める。

方針との関係
- 方針の内側に収まる。
- ポリシーに2つ足す。得点を GA4 に送ること（一覧に追加）と、URL の扱いの1文。
- 年齢にかかわる情報は集めない。ITパスポートには学生の受験者も多いとみられる（推測）。

不正・荒れ・法的な注意
- 正解は公開されているので、点は作れる。順位も景品も無いので、害は小さい。
- 過去に問題ページで解いた問題が号に入ると、点が上がる。号どうしの点の差を「伸び」とは書かない。

工数: M（6〜8日）。

効果の測り方
- weekly_view / weekly_start / weekly_complete / share_click {placement: weekly_result}。
- 1回目か2回目かは、端末の記録から作る値（区分B）なので送らない。復習（2回目以降）では weekly_complete を送らない。

```
https://shikakumon.com/chintai/?utm_source=x&utm_medium=social&utm_campaign=kiroku_day
```

着地ページ: 段階0では、既存の資格トップ。

必要な仕組み: サーバーへの保存は無い。

## 「一週間で一番正解率がいい」への答え

そのままでは作りにくい理由
- 比べる条件がそろわない。
  - /study/ の正答率は、各問の最後の1回の正誤なので、解き直すほど上がる。
  - そのうえ、人ごとに解いた問題が違う。
- 人数が足りない。週替わりの10問への参加は、全資格で週25人前後と見込む（推測）。資格ごとでは、週1人に届かない。
- 公正にならない。正解は、27の本番形式テストのページの HTML に全部入っている。問題ページにも答えがある。満点は誰でも作れる。
- 少人数の1位は、その人の X の投稿と突き合わせると、誰だか分かってしまう。
  - 未成年の利用者もいる。ITパスポート・知財3級・eco検定には学生の受験者が多いとみられる（推測）。未成年が特定されると、害はより重い。
- 「利用者どうしの順位を作らない」という方針と、正面からぶつかる。

そのまま作る場合の形と条件（受験番号ランキングを直した形）
- 形
  - 1資格・週替わりの10問。答えはサーバーで採点し、正解を端末に渡さない。
  - 名前ではなく、推測できない参加番号を使う（通し番号にしない）。
  - 正解数ごとのグループで示す（例「参加23件中、9問以上は10件」）。
  - 解いた時間で同点を分けない。景品は出さない。
  - 表示するのは、週を締め切ったあとの確定値だけ。10件未満の週は出さない。
  - 数えているのは人ではなく記録の件数なので、「記録N件」と書く。
  - 年齢・学年・学校は尋ねないし、集めない。
- 必要なもの
  - Upstash Redis と API 2本（開始と採点）、Turnstile。
  - 週のセットを、公開リポジトリに置かないこと（このリポジトリは公開されている）。
  - プライバシーポリシーの新しい節。書くのは次のこと。
    - 送るもの: 資格・週・10問の答え。
    - 保存するもの: 参加番号と正解数、正解数ごとの人数。
    - 保存しないもの: 名前・答え・端末の識別子。IP は、連投を抑えるために一時的に使う。
    - 消す時期: 週の終わりから28日後。
    - 削除の範囲。
- 工数: L（2〜3週間）と、毎週の点検。
- 起きうること
  - シークレットウィンドウで解き直せば、4択なら最大4回で満点になる。
  - 満点を大量に送る嫌がらせで、他の人の順位を下げられる。
  - 「学習のデータはサーバーに送らない」という約束に、例外が付く。
  - リーダーボードとバッジを入れた授業で、内発的動機と試験の点が下がった研究がある（https://www.smhp.psych.ucla.edu/pdfdocs/gamil.pdf 。docs/self-data-features-research.md の「作らないほうがよいもの」が、検索結果の要約から引いたもの。本文は読んでいない）。
- 作る条件: 次の両方を満たすこと。いまの数字では、当分届かない見込み。
  - 1つの資格で、同じ週に解き終える人（GA4 の利用者数）が、4週続けて閾値を超えること。
  - 未成年が特定されるおそれへの手当て（年齢にかかわる情報を集めない、少人数の週は出さない）が、上の形で足りていると判断できること。

代わりの形
1. 試験前の7日間の同じ10問（案1）で、「全問正解」を出す。名前の付いた1位ではなく、誰でも届きうる一番上の段にする。
   - 根拠: Duolingo の年間ふりかえりでは、共有の半分超が、XP 上位10%の利用者によるものだった（https://blog.duolingo.com/year-in-review-behind-the-scenes の検索結果の要約による。この数字がこの URL の主張かどうかは、修正の段階で確かめ直せていない）。
   - 1位の1人だけをたたえる形では、投稿する人がごく少なくなる。
2. 投稿した人との1対1（案1・案3）。同じ10問なので、比べる意味がある。
3. 方針を少し変えてよい場合
   - 窓が閉じたあと、運営が GA4 から「解き終えた回数（計測できた分）」を読み、次の回のページに手で書く。
   - 閾値を超えた回だけにする。
   - ポリシーの利用目的に「匿名の合計としてページに表示する」を1文足す。
   - 新しいサーバーは要らない。
   - 「いちばん正解が少なかった問題」は扱わない。MVP は問題ごとの正誤を GA4 に送らないので、読めない。送ると調査の区分C（問題ごとの状態）に当たり、方針の変更が要る。
4. 本人の過去の週との比較は勧めない。週ごとに、解いた問題の組と難しさが違うため（案5を参照）。

勧めるもの: 代わりの形の1と2を、MVP（案1）として先に出す。順位は、作る条件を満たす資格が出てきたときに、改めて検討する。

### 計測
- utm
  - X: utm_source=x&utm_medium=social&utm_campaign=shikenmae
  - LINE・共有・コピー: utm_source=line|share|copy&utm_campaign=shikenmae だけ
- GA4 のイベント
  - 新しい面なので placement だけを使い、place は送らない（docs/ga4-events.md の決まり）。
  - 送るのは、URL・日付・押した操作から決まる値（区分A）だけ。
  - 窓の間の2回目は、何も送らない。
  - 一覧
    - shikenmae_entry_click {exam, placement: cert_top|column|question_mid|question_end}
      - question_mid / question_end は、同じ行・カードの既存のリンクにそろえる。question_result は答え合わせの後の A8・Studio の枠の語なので使わない。
    - shikenmae_view {exam, placement: event|shared|archive}
      - placement は、URL と日付で決まる。
    - shikenmae_start {exam}
    - shikenmae_complete {exam, size, correct, score_bucket, mode: window|archive, shared: 1|0}
      - shared=1 は、着地ページ（点つきの URL）で解き終えたとき。
    - share_click {exam, channel: x|line|share|copy, placement: "shikenmae_result", with_score: 1|0, shared: 1|0}
    - practice_link_click {exam, kind: moshi|field|next_exam, placement: shikenmae_result}
- カスタム定義（公開前に、GA4 の管理画面で登録する）
  - 新たに登録するもの: channel、with_score、shared。channel は、いまの share_click でも未登録。登録しないと、送り先ごとの投稿率をレポートで分けて見られない。
  - 登録済みで、値の範囲が増えるもの: mode（window / archive が増える）。
  - 登録済みのもの: exam、placement、kind。
  - 送り始めるのは、ポリシーの追記を済ませてから。
- 見る比（窓ごと）
  - 投稿率: share_click(placement=shikenmae_result) ÷ shikenmae_complete(mode=window)。
    - 比べる基準は、段階0で確かめた「share_click の総数 ÷ moshi_complete の総数」。
  - 1投稿あたりの来訪: utm_campaign=shikenmae のセッション ÷ share_click。
    - 投稿した本人が、自分のリンクを開いた分も入る。
  - 来た人が解く割合: shikenmae_start ÷ shikenmae_view(placement=shared)。

## 作らないほうがよいもの

- 名前や、自由入力の表示名が付いた「週間1位」。常設の順位表。
  - 正解が公開されているので、満点は作れる。
  - 少人数の1位は、本人の特定につながる。未成年なら、害はより重い。
  - 方針ともぶつかる。
- 人数が少ないうちの、得点分布・平均・「上位◯%」。1人の点がそのまま分かってしまう。
  - 公開中に数分おきに更新する集計も作らない。差し引きで、投稿していない人の点まで分かってしまう。
- リンクに他の人の点を積み上げていくリレー（D2b・D3b）。
  - LINE のグループでは同時に開かれるので、リンクが分かれ、「このリレーの一番」が成り立たない。
  - 他人の点を、本人の確認なしに再掲することになる。
  - 「最高を更新」は、順位そのものでもある。
- 投稿を条件にした見返り（割引・抽選・機能の解放）。
  - ステマ告示の明示が必要になり、懸賞の規制も検討が要る。
  - 不正にごほうびを出すのと同じことにもなる。
  - 合格報告に謝礼を出さないという判断とも食い違う。
- OAuth による自動投稿。投稿は、intent から本人が送る形を保つ。
- 解いた時間で同点を分ける順位。自動で解くツールが有利になる。
- URL や画像に、自由な文字（名前・ひと言）を入れること。値を検証しないまま OG 画像を作ること。サイトの名前の入った画像を、好きな文言で作られてしまう。
- 年齢・学年・学校を尋ねる欄、それを表示すること。
- サイトが組み立てる文面で、合格と点を並べること。「合格者が使った10問」「予想問題」「的中」とうたうこと。「本番に出た」という声を載せること。本試験の問題に触れるよう促す文言を置くこと。
- 問題ごとの正誤（○×）を GA4 に送ること（調査の区分C）。
- 利用者の X 投稿を、サイトに引用・埋め込みすること。
- 運営が一般の利用者を装って、投稿やリレーを始めること。公式アカウントで出すなら、公式だと分かる形にする。
- 問題ページすべてに、新しい帯や枠を足すこと。8割強が「次の問題へ」を押す流れに割り込む。
- 試験前の10問の画面に、Studio の案内を出すこと。
  - これは docs/self-data-features-research.md の提案7が、直前の週について出したすみ分けの案（「直前の週には Studio の案内を出さない」）に合わせたもの。
  - 採用が決まった判断ではないので、ユーザーに確かめる。
- 前の週・前の回との点の差を、「伸び」として見せること。問題の組が違い、答えを覚えた分も混ざる。
- 人数が閾値に届かないうちに、Upstash などの新しい保存先を入れること（資格横断の段階2を含む）。

## ユーザーに決めてもらうこと

1. MVP の対象と時期。

2. 投稿した人との1対1の比較（着地ページで、投稿した人の点を並べる）を、方針の内側と見るか。
3. 投稿文の書き方を、いまの模試の投稿にも当てはめるか。
   - 宣伝の言い回しと「合格圏」を外す。
   - 資格名のハッシュタグを付ける。
   - 絵文字は使わない。
   - 本番形式テストの投稿名は、ページの名前「本番形式テスト」にそろえる。
4. 名前を「試験前の10問」にするか。直前対策コラムと混ざらないよう、「直前10問」は避ける案。

9. 案5の前提として、次の3つ。
   - 学習履歴に「いつ解いたか」を持たせるか。
   - 保存先を、調査の提案15 と同じ別のキー（shikakumon-daily-v1、端末のローカル日付、まとめて書く関数）にするか。

10. 方針を少し変えて、締め切り後の匿名の合計（解き終えた回数だけ）をページに載せるか。問題ごとの正答の多い少ないは、区分C なので扱わない。
11. 合格報告のお願いを出す期間を、合格発表日から14日まで延ばすか（案6）。X の企画とは別に価値がある。
12. 試験前の10問の画面に、Studio の案内を出さないか。調査の提案7の案に合わせるかどうか。
13. 法的な確認を、ステマ運用基準の原文を読むところまでにするか、専門家に確かめるか。
