# 姉妹ドリルのアクセスを本体シカクモンと同じ水準に上げるためのプロンプト

> シカクモン（本体、shikakumon.com）の姉妹ドリル 4 サイトの検索流入を、本体と同じ水準まで
> 上げるために、差を洗い、コードと執筆で直せるものはその場で直し、管理画面の作業は一覧にして返す。
> 月に一度くらいの頻度で回す。初回実施: 2026-10-31（結果は `docs/sister-traffic-audit.md`）。
> 2 回目以降は、まず `docs/sister-traffic-audit.md` の「未確認」を Search Console / GA4 の実数で埋めてから始める。

---

## プロンプト本文

あなたは資格試験サイト群の検索流入を伸ばす担当です。日本語でやり取りしてください。

対象は、本体シカクモン（`siken`、shikakumon.com）の姉妹ドリル 4 サイト。

| サイト | リポジトリ | ドメイン |
|---|---|---|
| 衛生管理者ドリル | `eisei-shikaku` | eisei.shikakumon.com |
| 設備資格ドリル | `setsubi-shikaku` | setsubi.shikakumon.com |
| 筋トレ資格ドリル | `kintore-shikaku` | kintore.shikakumon.com |
| 施工管理ドリル | `sekokan` | sekokan.shikakumon.com |

目標は **各ドリルの検索流入（Google の 28 日クリック）を本体と同じ水準に近づけること**。
基準線は本体の Google 28 日 2,447 クリック（2026-09-25 時点、`siken/CHANGELOG.md` 2026-09-25）。
本体の流入はコラム 55%・資格トップ 39%・問題ページ 2.2% で、ほぼ全部が「調べ物のコラム」と
「資格トップ」から来ている。本体のコラムは約 165 本、姉妹はそれぞれ 20〜46 本しかない。

問いは 1 つ。**本体が流入を取れている仕組みのうち、姉妹に無いもの・弱いものは何か。
それを姉妹ごとに、効く順に埋める。**

### 前提として読むもの

- 本体: `siken/CHANGELOG.md`（流入の内訳と問題ページ noindex の経緯）、`docs/growth-consulting-prompt.md`、
  `src/app/column/[slug]/page.tsx`、`src/content/columns/`、`src/lib/topic-hubs.ts`、`src/lib/exam-dates.ts`、
  `src/lib/inline-questions.ts`、`src/app/page.tsx` と `src/app/layout.tsx` の姉妹サイト一覧。
- 施工管理: `sekokan/docs/seo-gap-audit.md`（2026-09-26 の監査と実装の記録。重複させない）。
- 各姉妹の `CHANGELOG.md`・`docs/`・`src/data/site.ts`・`src/data/columns*.ts`・`sitemap.ts`・
  資格トップ・分野・1 問ページ・コラムのテンプレート。
- 数字は Search Console / GA4 の実数だけ。このセッションから管理画面と本番サイトには入れない。
  ユーザーからもらった数字か、コードと docs にある記録だけを使い、無いものは「未確認」と書く。
  推測を数字のように書かない。

### 見る観点（姉妹ごとに、それぞれ独立に）

1. **受け皿の量と形**: 本体のコラムの型（合格率・難易度 / 試験日・申込 / 勉強時間 / 過去問の入手先 /
   受験資格 / 意味ない / 履歴書 / 落ちたら / 直前対策 / 頻出数字 / 違い比較）を資格ごとに並べ、
   姉妹の資格 × 型で欠けているマスを数える。タイトルが検索語をそのまま含むか、資格別に分かれているか。
2. **本体にあって姉妹に無い仕組み**: 論点別ハブ（topic hubs）、試験日程と申込締切のカウントダウン、
   コラム内の 1 問（inline questions）、FAQ の構造化データ、合格報告、ガイド、学習の続き。
   流入に効くものと、回遊・収益にしか効かないものを分けて書く。
3. **発見の経路**: 本体 → 姉妹、姉妹 ↔ 姉妹のリンク（全リポジトリで grep）。本体の紹介文が
   今の資格数・問題数と合っているか。本体のコラム・資格一覧から、文脈の合う姉妹の資格へ
   リンクできる場所。
4. **テンプレートの title / h1 / description**: 資格トップ・分野・1 問ページ・コラムが、
   検索語（資格名 × 過去問 / 練習問題 / 一問一答 / 合格率 / 試験日）を含むか。本体と型が違うところだけ。
5. **索引の方針**: 本体は問題ページを noindex にした（2026-09-25、AdSense 再申請と
   サイト評価のため）。姉妹で同じ判断をするかは、Search Console の数字が無いうちは決めない。
   判断材料と、確かめる数字だけを書く。
6. **技術設定**: sitemap・lastmod・canonical・robots・RSS・IndexNow・llms.txt の差だけ。
   差が無いものは「差なし」と言い切る。
7. **需要と競合**: 資格ごとに主要クエリ（資格名 × 過去問 / 練習問題 / 合格率 / 試験日）を
   WebSearch で 2〜4 本引き、上位の顔ぶれと、姉妹が取れそうな隙間を書く。
8. **季節**: 今日から 8 週間以内に試験・申込締切がある資格。そこに先に手を打つ。

### 制約

- 所見は `file:line` か実際の数値を根拠にする。推測は「推測」と明記する。
- 過去問の転載、実績・監修者・利用者の声の捏造につながることはしない。
- 合格率・試験日・受験資格・受験料は、当該年度の公式案内で確認し、確認日と出典を残す。
  公式ページに入れないときは、検索ツールを公式ドメインに絞って本文の一致を見る。それでも
  確認できない値は書かない（「公式で確認」と案内する）。
- 設計言語（控えめ・非 AI 的な編集トーン・絵文字なし・事実の正確性）を崩さない。
  煽り文句・誇大表現・「最強」「完全網羅」の類を使わない。
- 既存の URL（スラッグ）は変えない。noindex・canonical・sitemap の方針は数字なしに変えない。
- 各リポジトリの prebuild の監査スクリプトと `npm run build` を通してからコミットする。

### 出力

1. 結論を 3 行（差の正体、姉妹ごとに 1 つだけやるなら何か、時間で解決する部分はどこか）。
2. 本体と姉妹 4 サイトの比較表（コラム数・資格数・URL 数・仕組みの有無・本体からのリンク）。
3. 姉妹ごとの所見を優先度順に: 見出し / 根拠 / なぜ流入に効くか / 具体策 / 工数 (S/M/L) /
   コードで完結するか手作業か / 反証になる観測。
4. 実施した変更（リポジトリ・ファイル・検証結果）。
5. 未確認と、確認する管理画面の場所（Cowork に渡せる形の依頼文つき）。
6. やらないほうがよいこと 3 つ。

### 進め方

1. 自分で読む: 各リポジトリの git log・コラム数・資格一覧・本体の姉妹サイト一覧。
2. `Workflow` で監査する。本体の「流入を取れている型」を 1 本で抜き出してから、
   姉妹ごとの監査（観点 1〜8）を並べる。同時実行枠が少ない環境（nproc が 4 以下）では
   姉妹ごとに 1 エージェントにまとめる。
3. 監査の結果から、姉妹ごとに「今すぐコードと執筆で直すもの」を決める。迷ったら、
   (a) 本体 → 姉妹のリンクと紹介文の更新、(b) 資格別の調べ物コラム（事実が確認できる型から）、
   (c) 本体の仕組みの移植（論点別ハブ・カウントダウン・コラム内の 1 問）、(d) テンプレートの title、の順。
4. `Workflow` で姉妹ごとに実装 → 検証（ビルド・監査スクリプト・事実の反証・トーン）→ 修正を流す。
   1 リポジトリにつき実装担当は 1 本（同じ作業ツリーを複数で触らない）。
5. 結果を `docs/sister-traffic-audit.md` に書き、各リポジトリでコミットして作業ブランチへ push。
   PR は依頼されたときだけ作る。
