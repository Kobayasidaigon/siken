# 論点解説コラム 生成プロンプト

検索流入(2026-08 実測で月 974 クリック)を増やすための、既存コラムとは別軸のコンテンツ。
このファイルをそのまま AI に渡して使う。

---

## なぜこの型なのか（背景。書き換える前に読むこと）

既存コラム 93 本は「とは / 合格率 / 勉強法 / 勉強時間 / 過去問 / 日程 / 意味ない / テキスト」を
10 資格へ横展開した型で、**ほぼ埋まっている**。ここに足すと骨格の同じ記事が増えるだけで、
検索エンジンから価値の薄い量産と見なされれば、増やすほど逆効果になる。

実測すると、既存 93 本どうしの類似度は中央値 0.046・99 パーセンタイル 0.155 と健全で、
閾値 0.45 を超えるのは `bijihou-nittei × jitsumu-nittei` の 1 ペアだけだった
(見出し 7 本中 5 本が完全一致。実施団体が同じ全情協なので中身も寄っている)。
**既存が悪いのではなく、これ以上同じ型を足すと崩れる**という状態。

そこで軸を変える。本サイトには 2,500 問超の解説があり、条文番号つきで、
2026-08 の是正 44 コミットぶんの検品を通っている。1 つの論点に複数問ぶんの
検証済み記述が溜まっているので、それを束ねれば新規調査なしに記事が書ける。
しかも論点ごとに中身が違うため、構造的に重複しない。

先行事例は `fukushi2-riyusho`（住宅改修の理由書とは？）。93 本中これだけが
「資格の情報」ではなく「論点そのもの」を扱っている。読者が試験の**前**ではなく
**勉強中・実務中**に検索する語を取りにいく型で、講座アフィリとも相性がよい。

## 手順

### 1. 書く論点を選ぶ

```bash
node scripts/topic-gap.mjs --min 6           # 候補一覧
node scripts/topic-gap.mjs --min 6 --json    # AI に渡す形式
```

出力は「問題数が多い順」であって「検索需要が多い順」ではない。
問題数はその論点に**検証済みの材料がどれだけあるか**を示すだけ。選ぶのは人間。

選ぶときの目安:

- **良い**: 資格名を外しても単独で検索される法令・実務用語
  （匿名加工情報 / 仮名加工情報 / 第三者提供の記録義務 / 外国にある第三者への提供）
- **避ける**: 教科書の章題のように一般的で、大手が強い語
  （情報セキュリティの脅威の概要 / 不正アクセス・サイバー攻撃の種類と対策）
- **避ける**: 法律事務所・弁護士メディアが圧倒的に強い一般民法語
  （消滅時効 / 抵当権 / 不法行為）。書くなら「貸金業の実務での扱い」に振り切る

### 2. 材料を集める

その論点の問題ファイルを**全部読む**。`--json` の `sampleQuestions` にファイル名が入っている。

```bash
node scripts/topic-gap.mjs --min 6 --json | node -e '…'   # or 手で開く
```

記事に書く事実は、**この解説にすでに書かれているものだけ**にする。

### 3. 書く（下の制約に従う）

### 4. 検証する

```bash
node scripts/check-column-dup.mjs      # 近似重複(閾値 0.45)
npm run build                          # 型・リンク・ビルド
```

## 制約（守れないなら書かない）

### A. 事実の出どころ

- 記事に書く条文番号・数値・要件は、**その論点の問題解説にすでにあるもの**から取る。
  解説にない条文番号を新しく書かない。うろ覚えで補完しない。
- 解説に無いが記事に必要な事実が出てきたら、**書かずに省く**か、
  一次情報（e-Gov 法令検索・個人情報保護委員会・各実施団体の公式サイト）で確認してから書く。
  確認していない事実を「たぶんこう」で埋めるのが、このサイトで最もやってはいけないこと。
- 制度・数値には作成時点であることを示す。改正が入る領域では特に。

### B. 重複を作らない（この記事の存在理由）

3 種類の重複を全部避ける。

1. **既存コラムとの重複**
   `src/content/columns/` の 93 本と骨格が被らないこと。とくに
   「〜とは」「難易度」「勉強法」「試験日程」の章立てを流用しない。
   その論点を扱った既存記事があるなら、そこへ内部リンクして**書かない**。

2. **新規記事どうしの重複**
   複数本まとめて作るとき、章立てを共通テンプレートにしない。
   論点ごとに構造が変わるのが正しい。
   「定義 → 要件 → 例外 → 罰則 → まとめ」のような型を全部に当てると、
   check-column-dup.mjs の閾値に当たる。
   **同じセッションで書いた記事の見出しを見比べて、5 本中 3 本以上で同じ見出しが
   出ていたら作り直す。**

3. **問題ページとの重複**
   1 問の解説を言い換えただけの記事は作らない。
   複数問にまたがる記述を統合して、**問題ページを読んだだけでは得られない
   全体像**（要件の関係、似た制度との違い、実務でどう効くか）を出す。
   出せないならその論点は記事にしない。

### C. 書き方

- 既存コラムの文体に合わせる。です・ます。断定しすぎない。煽らない。
- 読者は「その語を調べに来た人」。試験の宣伝から入らない。**まず語の説明をする。**
- 試験との接続は本文の後半か末尾で 1〜2 文。
  `fukushi2-riyusho` の「試験でも『理由書は誰が作成できるか』は頻出論点です」が手本。
- 表は使ってよいが、数値の羅列だけの表にしない。
- 見出しは論点の構造から決める。他の記事から借りない。

### D. 法務・広告まわり（違反すると提携が飛ぶ）

- **合格率・合格者数を、数値を伴って書かない。** 福祉住環境（fukushi2-*）は
  広告主ユーキャンが明示的に禁止しており、`lib/ucan-policy.ts` が
  合格率つき記事への講座広告を自動で止める。書くと広告が消える。
  他資格でも、講座紹介の文脈で合格率を数値で出さない方針は同じにしておく。
- 教育訓練給付制度に踏み込んで説明しない（ユーキャンの禁止事項）。
- 受講生の声・体験談を広告主のサイトから転用しない。
- 実在しない講座・コンテンツがあるかのように書かない。

### E. 内部リンク

- その論点の問題ページへ 1〜2 本リンクする（`/q/<slug>/`、資格により
  `/pii/q/<slug>/` 等。パスは既存コラムの書き方に合わせる）。
- 関連する既存コラムがあれば 1 本リンクする。無理に増やさない。
- リンクは本文の流れの中に置く。末尾にリンク集を作らない。

## 出力形式

`src/content/columns/<slug>.md` に置ける形で出す。

```markdown
---
title: "＜論点＞とは？＜その論点固有の切り口＞"
description: "＜120〜160字。何が分かる記事かを具体的に。資格名は入れてよいが主語にしない＞"
publishedAt: "YYYY-MM-DD"
updatedAt: "YYYY-MM-DD"
---

＜リード 2〜4 文。検索してきた人の疑問にその場で答える。前置きを書かない＞

## ＜論点の構造から決めた見出し＞

...
```

slug は `<資格接頭辞>-<論点のローマ字>` にする（例: `pii-tokumei-kakoujouhou`）。
接頭辞は `src/app/column/[slug]/page.tsx` の出し分けが効くので必ず既存に合わせること
（`pii-` / `chizai-` / `chizai2-` / `mynumber-` / `jitsumu-` / `bijihou-` /
`fukushi2-` / `bijimane-` / `eco-` / 貸金は `kashikin-` 等）。
接頭辞を間違えると、記事末尾に別資格の CTA が出る。
